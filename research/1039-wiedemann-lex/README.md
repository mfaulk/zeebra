# #1039: certified-Wiedemann lex pipeline against grobx's lex route

The data behind [`docs/research/wiedemann-pipeline-vs-grobx.md`](../../docs/research/wiedemann-pipeline-vs-grobx.md).

**Frozen at:** see `FROZEN` in `campaign.py` (tag `measured/1039-wiedemann-lex`). grobx 0.155.1 at `8005a2a1` (the #1029 pin), driver SHA-256 `fdd6aeec…83bc`.

| File | What it is |
|---|---|
| `probe.py` | Development-mode probe: any rows and arms, one record per attempt. Decides nothing |
| `campaign.py` | The deciding read: `inputs`, `manifest` (`tools/bench-job` publication jobs) and `extract` |
| `run-jobs.sh` | Runs the submitted jobs in order inside one CCD reservation, and releases it on exit |
| `summarize.py` | `tables.md` from the committed records: ratios, stage splits, routing regret |
| `probe-*.jsonl` | Development probe records (exploration and the operator census) |
| `records-<job>.jsonl.gz`, `.session.json` | One record per deciding attempt, extracted from each job's journal |
| `tables.md` | Generated by `summarize.py` |

The Zeebra side is `examples/lex_pipeline.rs`. Each process computes one complete lex basis by one
arm, with every stage inside `call_ns`, and prints one JSON line. Its `--input` is the grobx
driver's request JSON, so both engines read the same generator text. Its `--family` names are
generated deterministically:

| Name | Input | D | Class |
|---|---|---|---|
| `wd-N-d` | `x_i^d - x_{i+1}`, `x_{N-1}^d - x_0 - 1` (the `wiedemann_conversion` chain) | d^N | shape, radical, sparse operators; already a grevlex basis |
| `wdns-N-d` | `wd-N-d` plus `y^2 - 1`, `y` first | 2 d^N | non-shape control |
| `wdnr-N-d` | `wd-N-d` plus `y^2` | 2 d^N | nonradical, non-shape |
| `wdsq-N-d` | `wd-N-d` with the last generator squared | 2 d^N | nonradical, shape |
| `katsura-N`, `cyclic-N` | `grobner::benchmark_systems` | 2^(N-1); cyclic-6/7: 156, 924 | dense operators; cyclic non-shape |
| `pquad-N-s` | N dense quadratics in N variables with a planted point, seed s | 2^N | shape, dense operators |

## Reproduce

Build from the archive, so the bench-job provenance check holds. Keep target and temporary
directories on `/buildcache`, never `$HOME`. The example monomorphizes F4 and FGLM for 15 variable
counts and three fields; a fat-LTO build takes about 14 minutes.

```sh
git archive measured/1039-wiedemann-lex | tar -x -C "$SRC"
cd "$SRC"
export RUSTC_WRAPPER="" CARGO_INCREMENTAL=0
CARGO_TARGET_DIR=/buildcache/cargo-target/zeebra-1039-pub cargo build --release --example lex_pipeline
```

Development probe (no reservation needed; it decides nothing):

```sh
P=/buildcache/cargo-target/zeebra-1039-pub/release/examples/lex_pipeline
TMPDIR=/buildcache/cargo-target/zeebra-1039/tmp research/1039-wiedemann-lex/probe.py --pipeline $P \
  --rows wd-4-10,katsura-11 --arms grobx,adaptive,wiedemann,classical,direct-lex --cpus 40-47 --out probe.jsonl
research/1039-wiedemann-lex/summarize.py --dev probe.jsonl
```

Deciding read (publication mode; `bench-job run` takes the exclusive lock itself, so do not wrap
it in `bench-reserve run`):

```sh
export ZEEBRA_BENCH_JOBS=/buildcache/cargo-target/zeebra-1039/jobs
research/1039-wiedemann-lex/campaign.py inputs --pipeline $P --out /buildcache/cargo-target/zeebra-1039/inputs
for j in $(research/1039-wiedemann-lex/campaign.py jobs); do
  research/1039-wiedemann-lex/campaign.py manifest --job $j --pipeline $P --agent "$(scripts/agent/zb-claim.sh id)" \
    > /buildcache/cargo-target/zeebra-1039/inputs/$j.json
  tools/bench-job submit /buildcache/cargo-target/zeebra-1039/inputs/$j.json
done
setsid nohup research/1039-wiedemann-lex/run-jobs.sh <job-ids…> > "$ZEEBRA_BENCH_JOBS/runner.log" 2>&1 < /dev/null &
research/1039-wiedemann-lex/campaign.py extract --job "$ZEEBRA_BENCH_JOBS/<job-id>"
research/1039-wiedemann-lex/summarize.py > research/1039-wiedemann-lex/tables.md
```
