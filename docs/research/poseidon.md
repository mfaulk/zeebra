# Reduced-round Poseidon: what is faithful, what is reduced, and where the frontier is

**Measured at:** publication bound `ec83bc79` — the commits that published these figures,
recovered from git rather than recorded at the time ([§10](external-comparison-protocol.md#10-the-commit-and-what-a-publication-bound-is)).

Reference for M21-B (#93), which consumes #71, #78 and the measurement half of #79.

Reference implementation: <https://github.com/khovratovich/poseidon-tools>, commit
`60075da7c0521d9493749a035b1f30d4eda37138`, Apache-2.0.

## 1. What is taken from the reference, unchanged

| | |
|---|---|
| field | KoalaBear, `p = 2^31 − 2^24 + 1 = 2130706433` |
| S-box | `x^3` |
| round constants | 80-bit Grain LFSR, feedback `x^80 + x^62 + x^51 + x^38 + x^23 + x^13 + 1` |
| MDS | Cauchy, `M[i][j] = (i − t − j)^{-1} mod p` |
| round schedule | `R_F/2` full, `R_P` partial, `R_F/2` full |
| CICO variant | `permutation_plus_linear` — MDS before the first round, as the verifier uses |
| bounty instance | `k = 2`, `t = 16`, `R_F = 6`, `R_P ∈ {6, 8, 10}`, `C_1 = 0xc09de4`, `C_2 = 0xee6282`, `C_3 = C_4 = 0` |

**These are the real parameters, not toy substitutes**, and that is a checkable claim rather than
an assertion. The reference's README records

```
Poseidon(prime=2130706433, alpha=3, t=16, r_f=8, r_p=20).permutation([0]*16)[0] == 1393439926
```

and the port reproduces it. That single number exercises the LFSR's exact bit layout, its rejection
sampling, all 448 round constants, the Cauchy construction, and the round schedule — any of which
being wrong changes it. It is a committed test.

### 1.1 And every reduced configuration, against externally generated vectors

One published vector anchors the port at **one configuration and one coordinate**, and a reviewer
was right that it is not enough: the round *schedule* changes with `R_F` and `R_P`, and the
constants come from an LFSR seeded with them, so a reduced instance could in principle differ while
`t=16, R_F=8, R_P=20` still matched.

So every configuration the corpus uses has a vector generated by the Python reference and committed
here — `t = 2, 3, 4, 16` across `R_F ∈ {2, 4, 6}` and `R_P ∈ {0, 1, 2, 4, 8}` — compared across the
**whole output state**, in both `permutation` and `permutation_plus_linear`.

Two details that make them worth more than their count. The input is a ramp rather than zeros,
because the MDS layer maps zero to zero and the two variants would then agree — the test asserts
they *differ*, so a vector that tested one thing less would fail. And the vectors are pasted from
the reference's output rather than regenerated by this code, which is the whole point: the port and
the polynomial generator live in one Rust module, so a shared mistake in the round schedule would
be invisible to any test that compared them against each other.

### Not ported

`verify_mds_matrix`: the reference's subspace-trail, invariant-subspace and minimal-polynomial
checks on the MDS matrix. Those validate a *parameter choice*, not the round function, and the
matrix generated here is the same matrix the reference generates. Re-deriving its security criteria
would be reimplementing the reference's job.

The inverse S-box (`alpha = -1`) is out of scope: it has no polynomial form of bounded degree.

## 2. The polynomial system

The S-box is `y = x^3`. Carrying each state word as a polynomial in the inputs would give degree
`3^rounds` — unusable by the third round. So **every S-box output is a fresh variable**: with `L`
the affine form reaching an S-box,

```
y − L^3 = 0
```

degree 3 and no more, and the next round's words are affine forms in the new variables. Round
constants and the MDS layer contribute **no equations**: they are affine, and affine maps compose
into the forms.

| | count |
|---|---|
| variables | `(t − k)` free inputs + `t·R_F + R_P` S-box outputs |
| equations | `t·R_F + R_P` of degree 3, plus `k` affine output constraints |

Variables are ordered free-inputs-first, so the ones a specialization fixes are the low indices and
a permutation trace maps straight onto an assignment.

### 2.1 Faithfulness is checked in three ways

**Vanishing at a real trace.** `Poseidon::run` records every S-box output. A faithful system
vanishes at the assignment that trace induces, and `verify_against_trace` returns the indices of
the equations that do not — so a failure says *which part of the round schedule* is wrong.

**Corruption.** Vanishing at one point is necessary and not sufficient: the zero system vanishes
everywhere. So the tests corrupt each trace value in turn and assert that

- the corresponding equation stops vanishing — the system really depends on it, and
- no *earlier* equation breaks — nothing depends on a value computed after it.

Corrupting a free input must break the first S-box, which everything downstream depends on.

**Validated at construction.** `Poseidon::new` is bounded on `F: KnownOrder` and checks that `F`
really is the field `parameters.prime` names — a mismatched coefficient type produces a completely
different permutation while retaining the Poseidon metadata, and nothing about the result looks
wrong. `CicoInstance::new` requires exactly `2k` constants, because `system` and `is_solution`
index `constants[k + i]` and a short vector previously returned `Ok` and panicked later.
`CicoInstance::system` requires `N` to be **exactly** the variable count: a spare position is an
unconstrained variable, so the ideal gains a free coordinate and becomes positive-dimensional,
which is the same trap `Specialization::apply` fell into before its pinning equations.

**Planted targets.** A CICO instance with an arbitrary target may simply have no base-field
solution: at `t = 2, R_F = 2, R_P = 0, k = 1` with target zero, the solver returns
`NoBaseFieldPoint`, correctly. That is useless as a demonstration, because "found nothing" and
"is broken" look identical. So `CicoInstance::planted` runs the permutation on a chosen state and
takes its output as the target — a solution provably exists, and the planted value appears nowhere
in the generated system.

**And the recovered input is verified through the permutation, not the system.**
`CicoInstance::is_solution` rebuilds the state and runs `permutation_plus_linear`. A bug in the
generator cannot make that pass.

## 3. The relaxed verifier is not a polynomial condition

The bounty ships `verify_cico_solution_relaxed`, which accepts any output whose difference from
the target has its low `m` bits zero:

```python
diff = (state_out[i] - target) % p
if (diff & mask) != 0: return False
```

That is a condition on the **canonical integer representative** of a field element. `&` is not a
field operation and `(y − c) & mask == 0` is not expressible as a polynomial identity over `F_p`.
**Nothing here models it as one.** The systems generated are the exact reduced-round constraints;
the relaxed verifier is a thing to run against the reference implementation, and solving its bit
conditions needs a separate formulation — which is out of M21's scope and remains open.

The four bounty objectives — CICO, density, zero-test, partial collision — are also distinct and
are not conflated. Only CICO is generated here.

## 4. Where the frontier is

`cargo run --release --example poseidon_cico`. `k = 1`, planted targets, every row's system
asserted to vanish at a real trace before solving, every recovered input verified through the
permutation. `F4Options::max_matrix_columns` is capped at 60,000 so the failure is reproducible
rather than "it took too long on this machine".

| reduced to | variables | equations | outcome |
|---|---:|---:|---|
| `t=2 R_F=2 R_P=0` | 5 | 5 | solved, **0.8 ms** |
| `t=2 R_F=2 R_P=2` | 7 | 7 | solved, **156 ms** |
| `t=2 R_F=4 R_P=0` | 9 | 9 | solved, **371 ms** |
| `t=3 R_F=2 R_P=1` | 9 | 8 | **column budget crossed after ~18 s** |

The last two rows are the result. **Nine variables solve at `t = 2` and fail at `t = 3`** — same
variable count, different reach, because the MDS layer couples three words rather than two and
every S-box equation is degree 3. Variable count alone does not predict reach, which is the same
lesson M21-C's structural analysis refuses to draw conclusions from.

Note also what specializing does to a planted instance. Fixing one free input to a random value
almost surely excludes the planted solution, so the slices come back `EmptySlice` — correct, and a
clean illustration of M21-E's rule that an empty slice is not evidence about the system.

## 5. What this is not

The bounty instance is `t = 16`, `R_F = 6`, `R_P = 8`: **104 S-box variables** before the fourteen
free inputs, 118 variables and 106 equations. The frontier above is nine variables at `t = 2`. The
gap is not incremental, and **no result on a reduced instance says anything about the full one**.

`CicoInstance::reduced_from` carries the parameters an instance reduced *from*, for exactly this
reason: a result that did not say what it reduced would be misleading, and the field makes omitting
it a deliberate act rather than an oversight.

## 5a. Two programs, two objectives, and three targets still unsolved (M23-D)

The initiative has run **two** bounty programs, and they do not state the same problem. Read
2026-11-05 and re-read 2026-11-08 from <https://www.poseidon-initiative.info/>, with both readings
identical:

| program | objective, in its own words | window | status | claimability |
|---|---|---|---|---|
| 2026 CICO | `Perm(0xc09de4,0xee6282,X1,...,X14)= (0,0,Y1,...,Y14)` | within a program that "runs till January 1st, 2027" | "THE PROGRAM IS FINISHED"; all three tiers verified in 2026 | **finished** |
| 2025 bounty | `Perm(X1,..., X14,0,0)= (Y1,...,Y14,0,0)` | "runs till December 1st, 2025" | tiers claimed from Nov 2024 to Nov 2025; three never claimed | **expired** |

**The constrained words are at opposite ends**, and that is a different problem rather than the
same one with variables renamed: the MDS layer couples all `t` words, so constraining the leading
pair and constraining the trailing pair produce different ideals. `CicoInstance` constrains the
leading words, which is what the 2026 program asks for;
`Objective::CicoExactTrailing` names the other one and **nothing generates it**.
`ChallengeManifest::cico_instance` and `dispatch_cico` both refuse a row carrying it, by name,
rather than building the objective they do support — which would produce a different problem
wearing that row's identity, and nothing about the result would look wrong.

Three tiers of the 2025 program are listed as unsolved and are registered for that reason:

| id | field | `alpha` | `t` | `R_F` | `R_P` | solution status | stated reward | claimable? |
|---|---|---:|---:|---:|---:|---|---|---|
| `poseidon256-cico-2025-rf6-rp11` | BLS12-381 scalar field | 5 | 3 | 6 | 11 | **no public solution recorded**, 2026-11-08 | $10,000 | **no — expired** |
| `poseidon256-cico-2025-rf6-rp16` | BLS12-381 scalar field | 5 | 3 | 6 | 16 | **no public solution recorded**, 2026-11-08 | $15,000 | **no — expired** |
| `poseidon64-cico-2025-rf6-rp13` | Goldilocks `2^64 − 2^32 + 1` | 7 | 8 | 6 | 13 | **no public solution recorded**, 2026-11-08 | $15,000 | **no — expired** |

**The last three columns hold two different facts apart, and those facts moved apart.** The 2025 program's own
window — "Bounty program runs till December 1st, 2025", read 2026-11-08 — **closed on 2025-12-01**,
so the dollar figures are historical record and none of them is a live opportunity. The solution
status is unchanged and is the reason these rows are registered: they are still the only rows in
the registry with no public solution recorded, re-verified 2026-11-08 against the organizer's table
and corroborated by ePrint 2026/150, whose authors claimed the *lower* Poseidon-256 tiers and not
these. Solving one would still be a first public solution of a registered instance, which is the
research result; the prize is not part of it. Every programme's window, budget, verbatim status and
read date are in [`prize-ledger.md`](prize-ledger.md) §2, and no reward figure belongs in this
document without them.

Registered and deliberately not implemented: the first two are over a 255-bit scalar field and the
third over Goldilocks, neither of which this generator is wired for, and all three use the trailing
objective. A scoreboard that listed only what it can run would hide exactly the problems that are
open — these are the only rows in the registry with no public solution recorded.

**What this says about M23-B's ladder.** The 2025 program's Poseidon-31 tiers at `R_F = 6` with
`R_P` up to 4 were claimed between November 2024 and November 2025, at `t = 16`. M23-B's
`R_F = 6, R_P = 4` row stops at degree 4. Those are *different objectives* over fields that differ
in one case (M31 against KoalaBear), so the comparison is not apples to apples — but it is evidence
that round counts of that order at `t = 16` are reachable by some attack, and not by this one.

## 6. Open

- **The relaxed verifier's bit conditions** need a formulation that is not a field equation. §3.
- **Alternative formulations** (#79) — the measurement here is that the S-box-per-variable
  formulation reaches `t = 2` at nine variables; whether a different one reaches further is the
  question, and this is the baseline to beat.
- **`t = 16` at any round count** is far out of reach, and the interesting question is which of
  #74–#76 or #82–#85 moves it.
- **Degree-3 equations with a dense MDS layer** are the structural obstacle, not the variable
  count. A formulation that kept the MDS sparse — or eliminated the partial-round words
  structurally — is where §5's resultant and CICO track would start.
